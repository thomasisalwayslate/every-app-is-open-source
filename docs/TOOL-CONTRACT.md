# The seven tools

All argument objects are closed: unknown keys, wrong JSON types, missing required fields, invalid enums and out-of-range numbers are rejected. A string `"false"` is not a boolean; a boolean is not accepted as an integer. Strings are limited to 10,000 characters. MCP request lines are limited to 1 MiB characters. Validation runs before Ghidra initialization.

| Tool | Required input | Optional input / bounds | Result |
|---|---|---|---|
| open_program | none | full: boolean; local unreleased: analysis_mode full/quick, cancel boolean | In MCP: starts/checks analysis and returns live status until ready. Once ready: captured-input hash, architecture, memory map, function count; full metadata on request |
| search | none | kind: strings/functions; pattern: string; offset >= 0; limit 1–200; full: boolean; local quick functions: index_cursor or view (<=256 chars) | Defined strings/functions plus supported Go metadata names and literal matches, references and next page |
| inspect | addresses: 1–8 strings | mode: decompile/outline/assembly/references/calls/all; full; offset/column >= 0; limit 1–80; find or focus; context 0–20 | Outline first, then matching lines or focused snippets; bounded pages last |
| read_memory | address: string | length: 1–65,536; format: hex/utf8/both; optional layout: go_strings with count and offset | Static analyzed-image bytes, explicit loader initial zeros or bounded Go descriptors; unavailable regions remain explicit |
| calculate | expression: string | Restricted expression AST, <= 2,000 nodes | Computed expression value; does not verify the expression's premises |
| decode_swift_string | words or address | words: two unsigned 64-bit integers or integer strings | Computed Swift small-string decode; pointer-backed layouts fail |
| read_evidence | id: returned 32-character hex ID | offset >= 0; limit 1–40,000 characters | Content-checked saved evidence, paged |

Pseudocode and recovered types/call graphs are **computed** static interpretations. Literal instruction bytes and initialized analyzed-image reads are **facts**; synthesized loader initial zeros and Go descriptor interpretation are **computed**. Neither proves an interpretation of the program's intent. Indirect calls, undefined strings, unsupported Swift layouts and truncated previews can require more investigation. Full evidence retains the result behind a short preview.

## Focused inspection

Released 0.1.5 exposes the bounded views below; 0.1.6 adds compact paired-focus and call-list changes.

- A single small function can return its code. Above 5,000 characters, the default is an outline, rather than a head preview: size, callees with call-site addresses, referenced text previews, return sites and error candidates. Error candidates are **name-based hints**, not proven error paths. Callees retain first-call order, with Go runtime/internal helpers last. Outline categories include totals and independent next offsets; `mode="outline"` with `offset` pages them.
- A request for multiple code functions returns outlines, even with `full=true`. Ask for one address to read code. This prevents eight whole functions arriving together.
- Start with the outline; use `find` or `focus` to narrow the investigation. Read sequential code pages only when those views are insufficient. `find={kind: "text", value: "<literal>"}` searches rendered lines case-insensitively, without regular expressions. `find={kind: "constant", value: "422"}` (or `"0x1a6"`) compares lexical decimal/hex integer tokens, ignoring quoted text and comments; it does not evaluate expressions, floating-point values, types, signed bit patterns or values built across instructions. It works on one function in `decompile` or `assembly` mode. It does not search referenced memory: use the top-level `search` or string `focus` for that.
- Search replies contain only matching lines with small context (two lines on each side by default), one hit per line, available instruction addresses and original line/column positions. No guessed address replaces an unmapped C line. Context and long text can be shortened to preserve the match within the reply budget. At most eight matching lines arrive per reply, further reduced by `limit` and a 6,000-character match-list budget. `find.next_offset` resumes **matching lines**, not code lines; repeat the same query, mode and function with that top-level `offset`. Totals describe rendered-line matches, not all runtime values. Empty matches do not prove the value is absent from the program. `find` cannot combine with `focus` or a column cursor.
- For one function, `full=true` returns one code page, up to 6,000 characters and `limit` lines (40 by default, at most 80). The first page of a large function also includes a compact outline. Follow the returned `next: {offset, column}` with the same function and mode. Offsets are zero-based; displayed line numbers are one-based. The column cursor preserves long single lines without lost or duplicated text. `next=null` means the end. Earlier code may be omitted when a page starts in the middle.
- `focus={kind: "address", value: "<instruction address>"}` selects a mapped instruction. `kind="string"` accepts a referenced text address or **text prefix**; a substring found only in adjacent packed text is not attributed to the earlier reference. `kind="call"` accepts a callee address or name fragment. Use `occurrence` (zero-based, inside `focus`) to move between matches, following `next_occurrence`. `context` defaults to six lines on either side; `limit` and the character budget can reduce that window.
- A focused snippet is surrounding pseudocode, **not a data-flow or control-flow slice**. Omitted checks can matter. Ghidra Clang tokens and pcode PCs supply the line mappings. When a matched instruction has no mapped line, the result explicitly returns a bounded **assembly-only** window. It never substitutes the nearest pseudocode line. A missing match is not proof of absence. Focus cannot leave the selected function.
- `mode="assembly"` also accepts all three focus kinds, returning a window around the actual matching instruction. Assembly focus uses instruction/data-reference metadata directly and does not require successful decompilation. Its match line number is an instruction-list index, not a C line. Search/focus selection is labelled `computed`; literal instruction bytes remain observations.
- Assembly, incoming references and caller/callee lists also page with `offset` and `limit`. Full evidence retains complete requested native lists. Code batches are bounded to 16,000 serialized data characters plus list separators; code pages are capped at 6,000 characters. Totals and continuation cursors survive list trimming.

Examples (use addresses discovered from your own target):

```json
{"addresses":["<function entry>"],"focus":{"kind":"string","value":"<text prefix>"},"context":10}
{"addresses":["<function entry>"],"focus":{"kind":"call","value":"<callee name>"},"context":6}
{"addresses":["<function entry>"],"find":{"kind":"constant","value":"422"},"context":2}
{"addresses":["<function entry>"],"mode":"assembly","find":{"kind":"text","value":"cmp"}}
{"addresses":["<function entry>"],"mode":"assembly","focus":{"kind":"address","value":"<instruction address>"}}
{"addresses":["<function entry>"],"full":true,"offset":80,"column":0,"limit":40}
```

Read-only text previews are at most 256 bytes; Go pointer/length candidates are explicitly labelled `guess`, not verified string objects; raw text previews are `fact` and reference/code interpretations remain `computed`. Outlines scan at most 100,000 instructions and retain at most 2,048 string-reference previews per function, with incomplete coverage reported. Optimized instructions and nonstandard string constructions may lack mappings or previews. Existing raw memory, assembly, call/reference inspection and content-checked evidence remain available. Full function code and line/address mappings are saved alongside each result, including the exact returned view. An in-process cache retains at most 64 function views / 32 MiB of serialized data (Python/Java overhead is additional); it does not modify Ghidra or prior evidence.

## MCP analysis status (published 0.1.6)

Version 0.1.2 keeps the same seven tools. The first binary-dependent request starts one owned analysis process, waiting up to five seconds for a quick/cached load. If initialization continues, `open_program` returns `classification: fact`, scope `analysis status; no program result`, and `data.analysis` with `state`, `stage`, `elapsed_seconds`, `stage_elapsed_seconds`, `worker_alive` and the captured input `sha256`. This live status has no evidence ID and is not a decompilation claim. Version 0.1.1 did not provide this live status.

Stages are coarse boundaries EAOS observes: `starting`, `importing`, `loading_cache`, `analyzing`, `saving`, optionally `indexing_go`, then `ready`. They are not Ghidra's internal analyzer messages. Elapsed time and a live worker do not prove forward progress, provide a percentage, or establish time remaining. A failure retains its error and does not silently restart on status checks. After a busy-program-lock error, close the other process and explicitly call `open_program` again to retry. Other initialization failures require a server restart after addressing the error.

While initialization runs, `search`, `inspect`, `read_memory` and decoding at a program address return `isError: true` with `analysis` status instead of accessing partial analysis. Pure calculation, decoding supplied words, saved-evidence retrieval, `ping` and the catalog remain available. When ready, tools return their documented results. Poll with `open_program` when asked or at a deliberate later checkpoint, not continuously. Native requests after readiness still execute serially.

The process belongs to this MCP server. Closing the client connection ends unfinished work; there is no detached job or resume guarantee. Do not promise continued analysis after client shutdown. A completed project is reused, and interrupted work may need to run again. No input program is executed. Terminal `eaos call` remains synchronous and waits for the requested result.

Read-only native analysis still parses untrusted input using Ghidra/Java/native code and is not an OS sandbox. See [SECURITY.md](../SECURITY.md). Initial analysis has no overall deadline. No per-analysis cancel tool is provided; closing the server ends its owned worker. Do not describe all expensive work as fully bounded.

## Go discovery

Go discovery uses the existing search/inspect tools. On detected Go programs, `open_program.data.go` reports the embedded compiler version when its inline build-info encoding is supported, metadata-name availability, parser version and literal-scan coverage. Unknown build-info versions do not establish that a binary is not Go. Go discovery does not replace Ghidra's version-specific type/ABI analysis.

`search(kind="functions", pattern="...")` merges recognized Go pclntab names and Ghidra functions by entry address. `source: go_pclntab` means a name was parsed from retained artifact metadata; it does not recover original source. Duplicate names at different entries remain separate. `inspect` enriches an analyzed function with its Go name and retains `ghidra_name`. A metadata entry without a Ghidra function is explicitly marked `analyzed_function: false`; inspection fails honestly rather than manufacturing pseudocode. Metadata offsets and table provenance are retained in full evidence.

For nonempty string patterns, Go search also scans initialized, read-only, non-executable blocks, excluding named pclntab. `source: literal_bytes` and `extent: match` identify a **matched slice**, not a complete Go string object. Go literals can be packed, contain zero bytes and occur inside longer strings. ASCII byte search is case-insensitive; other UTF-8 literals require exact bytes. Defined-string search retains its Unicode case folding. Empty patterns list only Ghidra-defined strings. Coverage describes this literal scan, not every possible string, function or runtime value in the application.

References come from Ghidra's stored reference manager at the actual matched address. They are computed static links, and can be empty even when a human can see address construction in assembly. No hidden whole-program decompilation or inferred reference pass runs during search. On a stripped Go 1.25.14 fixture, some discovered literals had no stored references; this remains a limitation. Raw match bytes are observable; address mapping, decoded names and reference interpretation are computed. Assembly with recovered Go names is therefore labelled computed as a whole.

Default search previews cap text at 256 characters and references at eight, preferring code references. Totals and truncation are explicit. `full=true` expands the result; `read_evidence` retrieves the saved record. Reference collection is capped at 4,096 per hit; `references_complete: false` makes the reported count a lower bound. Raw literal matches stop at 10,000 and report incomplete coverage; refine the query. Literal indexing and metadata scanning each have a 64 MiB budget, and metadata parsing accepts at most 500,000 entries and 4,096 bytes per name. Oversized or unsupported metadata produces an availability error while ordinary Ghidra capabilities remain usable.

In published 0.1.6, Go name indices are stored beside the selected program in `eaos-analysis/<digest>/go-index-v1.json` with a checksum, bound to the captured target, metadata bytes and parser version. Existing Ghidra projects are reused; Go indexing does not increment `analysis_count` or rewrite historical evidence. Replaced invalid indices are retained alongside the cache. Closing the MCP server stops its owned indexing worker.

The parser recognizes Go 1.18 and 1.20 pclntab layout families, not every future compiler or executable mapping. Native integration has been checked on stripped darwin/arm64 fixtures compiled with Go 1.25.14 and 1.27.1. Multi-section text, obfuscation, absent metadata, unusual load mappings and unsupported layouts may fail discovery. No broader platform, decompilation-accuracy or agent-performance claim follows from those checks.

## Static memory and Go tables (0.1.6)

`read_memory` inspects the selected captured program, never a live process. Initialized bytes come from Ghidra's analyzed image and can include loader fixups. Complete reads of initialized bytes keep the compact address/length/requested-format response; segment provenance, UTF-8 validity and static-image caveats remain in saved evidence. Reads involving initial zeros or unavailable bytes report segment origins and whether the requested range was complete; they never skip a gap and concatenate later bytes. An entirely unmapped start is an error. Other unknown/uninitialized memory returns an explicit unavailable segment. Only validated thin Mach-O section commands authorize initial zeros; fat headers and other formats do not gain guessed zero-fill support. Invalid metadata cannot authorize zeros. Segmented reads stop after 64 segments and report a continuation only for that budget limit.

A verified zero-fill segment returns `origin: loader_zero_fill` and **computed**, with its section provenance: “Initial loader state only; current runtime contents are unknown.” The tool does not modify Ghidra memory. Swift decoding from an address requires all 16 bytes to be initialized analyzed-image bytes; synthetic initial zeros or partial/unavailable reads are rejected.

For an explicitly identified Go pointer/length table, use `read_memory(address="<table>", layout="go_strings", count=18, format="utf8")`. `count` is the total number of descriptors (1–1,000,000); `offset` is a descriptor index, not a byte offset. Layout requests require count and cannot also specify length. Pointer size and endianness come from the selected program. No null termination, string-boundary inference, target execution or recursive pointer following occurs.

Each page decodes at most 32 descriptors, with at most 256 preview bytes per string and 8,192 total payload bytes. The compact response also respects the inspection reply budget and can return fewer items; follow its `next_offset`. Raw descriptors, payload bytes, provenance and derivations remain in content-checked evidence, which may require paging to retrieve fully. Empty, invalid, partial and unavailable entries retain their indices. An unavailable descriptor is never interpreted as an empty string. UTF-8 replacement display is marked with `utf8_valid: false`; validity refers to preview bytes only, and a cutoff can split a valid multibyte character. Raw hex remains in evidence. This is computed static interpretation, not proof of runtime strings.

Use `mode="all"` with focus to retrieve bounded pseudocode and matching instruction context in one request; code-only decompile focus stays small. A missing instruction mapping is explicit. Focused all-mode previews omit unrelated caller/callee pages, retained in full evidence. The existing occurrence selector remains; no extra multi-focus schema is introduced. This is surrounding code, not a control-flow slice. Instruction text previews cap at 256 characters; instruction bytes remain available.

Call-list mode honors limit up to the existing maximum of 80 instead of an unconditional cap of 40. Character limits can still shorten a page. Returned counts and each list's next offset describe what actually appeared. Defaults remain small. These are workflow changes, without a new agent speed, token, cost or accuracy claim.

## Local 0.1.7 analysis profiles and identity

This section describes unreleased source changes. Published 0.1.6 commands do not accept these options. The seven tools remain unchanged. CLI `mcp` and `call` accept `--architecture auto|arm64|arm64e|x86_64`, `--analysis-mode full|quick`, `--analysis-timeout` and `--request-timeout`. Full analysis is still the default; `full=true` remains output verbosity only.

On Apple Silicon, a compatible universal input selects actual ARM64 slice bytes (ARM64e fallback), rather than relabelling an x86 import. Explicit architecture choices reject unavailable or ambiguous slices. Thin inputs retain their architecture. Validation checks bounded slice metadata, alignment, overlap, inner CPU/subtype, selected bytes/hash and the Ghidra language/compiler. ARM64e selection is not a complete pointer-authentication/decompilation guarantee. The immutable original container is retained; a universal input also gets a derived read-only slice. Cache identity includes the whole-file hash, slice identity, profile, Ghidra version and index version. New projects and Go indices live in `eaos-analysis/<whole-sha>/profiles/<identity>/`; old projects remain untouched and are not reused by the new format. The target-wide lock prevents competing profiles from owning the same capture.

`search(kind="functions")` matches available short names, class/namespace-qualified names, signatures and bounded aliases. `qualified_name` is omitted when identical to `name`. Distinct entries with duplicate or overloaded names remain separate; clients must use the returned address. External functions retain their `EXTERNAL:` address space, are marked `external`, and have no imported instruction body. External data symbols are not claimed to be functions. Alias collection is capped at 128 symbols/aliases per entry (four preview aliases); truncation is explicit. There is no startup pass demangling every symbol, nor a guarantee of original Swift name recovery.

Quick mode supports 64-bit ARM/x86 Mach-O. It imports loader names, runs bounded Objective-C metadata recovery and exposes read-only literal-byte matches before full analysis. Other Swift names appear only where available from the loader or supported metadata. Literal indexing retains at most 16 MiB of initialized read-only non-executable blocks; matches are byte slices, not complete string objects. Candidate-name indexing starts with at most 50,000 function starts and a two-second iteration budget, with a further 8 MiB payload limit per batch. It never silently expands through ordinary result pagination. Explicit continuation uses the same bounds; candidate-query processing has a separate two-second budget. Commit IO and existing metadata enumeration also remain subject to the configured native-request deadline. These iteration/query limits are not a two-second guarantee for the entire search call. Available counts describe parsed `LC_FUNCTION_STARTS` candidates, not every function in the program. Omitted entries and empty references do not establish absence. Go's existing bounded metadata discovery is still distinct from Ghidra ABI/type recovery.

Inspection prepares only requested functions: at most 64 KiB candidate extent, 8,192 instructions, branch depth 128, 15 seconds per preparation and 1,024 prepared functions per quick profile. `LC_FUNCTION_STARTS` supplies a candidate ceiling, **not a verified whole body**. Reachable instructions and ownership determine the prepared body; overlapping ownership and unsafe boundaries refuse the request. Unresolved indirect jumps, direct tail edges or missing instructions retain `assembly_partial` with explicit limitations; pseudocode requires `flow_prepared`, which still does not prove semantic completeness. Useful assembly remains available when decompilation fails. A prepared function does not make other functions or the program analyzed. Mutation invalidates cached views, candidate names, references derived from those views and decompiler state. Quick caches store and validate per-function body hashes/revisions and are never marked fully analyzed.

Every affected `open_program`, `search`, `inspect`, `read_memory` and address-decoder response, including compact output, carries `analysis` coverage; evidence adds full identity and actual language/compiler provenance. Function rows retain their own readiness where relevant. Full-mode `whole_program_pass` means the configured pass finished, not complete recovery. Literal bytes are facts; pseudocode, decoded names, instruction interpretations and synthesized zeros are computed; inferred interpretations remain guesses. Structured records and `artifact-<sha256>.c` raw pseudocode are content-addressed and immutable. Earlier evidence IDs remain readable from the shared capture evidence directory across profiles, including legacy evidence.

`open_program` with `analysis_mode="full"` explicitly opens the separate full profile; it neither promotes the partial project nor erases it. It can return loading status before that profile becomes ready. A live native operation must finish or be cancelled before changing profiles. The CLI provides the same explicit choice. Full mode retains the existing whole-program analysis path.

The stdio reader stays responsive during native operations. `ping`, the catalog and status can respond while the single native owner works. Other native requests are serialized or return a busy/status error; no detached jobs are launched. Operation status includes elapsed time and its deadline, with no percentage, forward-progress or ETA claim. Initialization defaults to 3,600 seconds and a native request to 120 seconds; CLI flags allow 0.05–7,200 seconds. Objective-C metadata has a 30-second monitor budget; decompilation is limited to 20 seconds quick / 60 seconds full. The owning process enforces the overall deadline if a native monitor does not respond.

`open_program(cancel=true)`, `notifications/cancelled` for an outstanding request, client EOF or server shutdown stops owned native work. Accepted cancellation immediately enters `cancelling` and blocks new native work, including profile switches. Worker shutdown runs away from the stdio reader; ping and status remain available while it waits. Status retains the stopping worker's liveness until it exits, then reports `cancelled`. The shutdown thread is owned and joined by the session, not a detached analysis job. Cancellation/deadline expiry requires restarting the session; there is no silent retry or resume guarantee. Busy target locks remain retryable on an explicit open after the other owner closes. Status has no evidence ID; analysis results do. Terminal calls wait synchronously under the same owner/deadline mechanism. These controls do not create an OS sandbox.

### Bounded function-discovery continuation (local, unreleased)

Use the existing `search` tool in the quick profile. The seven-tool catalog is unchanged. Full-profile search retains offset pagination and rejects discovery cursors before native startup; this feature does not start whole-program analysis.

```json
{"kind":"functions","pattern":"handler","limit":10}
{"kind":"functions","pattern":"handler","offset":10,"view":"<data.view>","limit":10}
{"kind":"functions","pattern":"handler","index_cursor":"<data.coverage.function_candidates.next_index_cursor>"}
```

- **Result pagination:** use `next_offset` with the returned `view` and the same query. It pages matching functions already available in that view and never indexes another candidate. Positive quick-function offsets require `view`. `has_more_results` is explicit; `next_offset=null` describes only this view's results.
- **Index continuation:** pass `next_index_cursor` as `index_cursor`, with offset zero and no `view`. It commits at most one more bounded, contiguous prefix extension. The cursor is global to this profile's candidate index, so the next search pattern can differ. There is no detached job, automatic loop, candidate skipping or implicit continuation.
- Results after expansion are **cumulative**, sorted by address identity. Expansion starts a new view at offset zero: previously seen entries can appear in that new view, but never duplicate within a result set. Finish the old view before expanding, or restart paging and use address identities. Old views and already-consumed index cursors are rejected with a recovery message, rather than silently shifting offsets. A query change also invalidates its result view. A zero-progress batch retains its position/cursor and explains the stopping reason; retry is explicit.

Both compact output and saved evidence retain `coverage.function_candidates`: `candidates_indexed`, `candidates_available`, `index_complete`, `truncated`, `reason`, last `batch_start`/`batch_end`, `batch_limits`, `can_continue`, and `next_index_cursor` (or null). Reasons are `complete`, `candidate_limit`, `time_limit`, `byte_limit` or `storage_limit`. `matches_scope` states that matches cover currently available metadata plus the committed candidate prefix; incomplete discovery is a lower bound, never proof of absence. Candidate-index completion means every parsed candidate was visited, **not** complete symbols, strings, references, program analysis or original-source recovery.

Function rows distinguish `ghidra_function`, `external_function`, `go_pclntab` and `function_start_candidate` sources. Matching metadata takes precedence at a shared internal entry; external address spaces remain separate. Duplicate names at distinct entries survive. Short/qualified names and bounded aliases are searchable. Candidate names cap at 4,096 characters, alias inspection at 128 symbols / 16 KiB of alias text; truncation is explicit. Existing compact previews remain shorter. No whole-binary demangling or semantic ranking is performed.

The derived `function-index-v1.sqlite` lives inside the existing architecture/profile directory, uses Python's standard-library SQLite, and contains candidate rows and their committed high-water mark in one transaction. It is bound to the existing captured-input/selected-architecture/profile/engine identity, discovery schema and verified analysis revision. The storage budget is 256 MiB of accounted payload plus SQLite overhead, including extra journal space during a batch. `storage_limit` leaves discovery incomplete with `can_continue=false`; no automatic eviction or full-analysis fallback occurs. Known-address inspection remains separate.

Continuation strings are strictly typed state identifiers, never paths, SQL or expressions. Malformed/foreign/stale cursors do not reset progress or alter earlier evidence. Recovery normally means `search(kind="functions", offset=0)` without either cursor, then use the freshly returned tokens. Missing/incompatible/corrupt index files fail explicitly and remain preserved; after closing the owner, preserve/move only the derived index and its journal to regenerate it. This does not require deleting the Ghidra project or evidence. Tokens are consistency checks, not security credentials or protection against a malicious local user.

A failed or cancelled uncommitted batch rolls back; a completed batch may already be committed if cancellation arrives after commit. Reopen with an ordinary query to discover the retained position. A cursor whose batch committed is stale and must be refreshed, not replayed to skip another range. Completed indexes reopen without automatic expansion. SQLite crash recovery preserves either committed prefix; structurally inconsistent state is rejected. Discovery-only expansion changes the result-view position, not the Ghidra analysis revision or pseudocode. Existing view invalidation closes the derived index after analysis mutation. The next ordinary query regenerates its derived rows against the verified new revision; old continuations/views reject. Earlier structured evidence and raw pseudocode remain unchanged and readable across expansion, reopening and invalidation.

Preparing a previously unprepared function is an analysis mutation, even when the requested output is only assembly: disassembly, references and function ownership can change. The conservative revision invalidation remains intentional. Inspecting an already prepared function reuses readiness and does not itself advance the revision or discard candidate progress. Each candidate query checks all committed rows before returning its page/count, including rows whose cached names do not match; corrupt search keys cannot silently become absence claims. Integrity scanning shares the existing query deadline and can fail explicitly on large prefixes without returning a partial count. Reopening also validates accounted payload totals and finite batch limits. These checks detect inconsistent stored data; they do not authenticate a cache against a malicious filesystem owner.

Evidence retrieval verifies its checksum, content-derived ID and selected target identity. Copying a valid record from another target into the directory does not make it evidence for this program. Rejected records and earlier evidence remain untouched.
